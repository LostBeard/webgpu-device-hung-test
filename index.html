WebGPU device hung test

Does your GPU lose the WebGPU device after a compute kernel with large function-scope arrays?

On an NVIDIA RTX 4070 (Windows, Chrome, D3D12 backend), the sequence below always ends in DXGI_ERROR_DEVICE_HUNG: a kernel holding more than 1652 32-bit ints (6608 bytes) of dynamically indexed function-scope arrays per thread, then any other dispatch in the same submit, then (after the GPU went idle) a later large kernel loses the device. There, 1652 ints never does it, 1653 always does, and a queue submit right after the large kernel prevents it. We do not know yet which GPUs are affected. Running this page and reporting the result helps answer that.

Before you run the test: on an affected GPU the screen may go black for a moment while Windows resets the display driver, and the browser may turn WebGPU off for this tab. Save your work first. Nothing is uploaded: the page only replays WebGPU calls locally, and the report below is sent only if you choose to open the GitHub issue.

How it works

The page replays a recording of every WebGPU call a real page made (a VP9 decode, then an encode, compiled to WGSL by SpawnDev.ILGPU). No application code runs: replay.js reissues the recorded calls in order and waits on each promise where the original page did. The decoder's two kernels were replaced by a small synthetic kernel (one thread loops over two function-scope arrays and touches no memory); the kernel that loses the device later is the real encoder kernel. Sources, the trace builder and details: github.com/LostBeard/webgpu-device-hung-test.
